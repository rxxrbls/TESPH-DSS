## Upload and data-lifecycle contract

`final_outputs/*.csv` is the historical Member 1 handoff generated by
`final_etl_handoff.py`. The integrated app reads the prepared-transaction
baseline as input to its separate local runtime authority rather than replacing
it with the most recent upload.

`final_outputs/prepared_transactions.csv` is the immutable governed historical
baseline. After a successful upload, the local application reconciles validated
staging rows against the active history and atomically publishes the consolidated
prepared transactions, materialized Star Schema, and ingestion audit at
`runtime_data/active_transactions.db`. The governed `final_outputs` handoff is
never rewritten by normal uploads.

The application is designed for local, single-operator capstone use. Concurrent
sessions are not guaranteed to share one consistent dataset: a later upload can
replace the global SQLite snapshot while another session keeps its own in-memory
`ETLResult`.

For the local authorized-user login, copy `.streamlit/secrets.toml.example` to
`.streamlit/secrets.toml` and set the `[auth]` values. The real secrets file is
ignored by Git. Temporary local development may instead set
`TESPH_AUTH_USERNAME` and `TESPH_AUTH_PASSWORD` in the process environment.
Settings profile email changes require the `[email]` SMTP configuration (including
`app_base_url`) and remain inactive for password recovery until the emailed
verification link is opened. Username changes are stored in the local account
database and become the login name after the profile is saved.

## Data Lineage

The data dictionary uses three lineage labels:

### `Source`

The value comes directly from the original Shopee export and is preserved as source information.

Examples:

- Product Name
- Variation Name

### `Cleaned Source`

The field originates from Shopee but was safely parsed, normalized, or standardized during ETL without inventing a new business value.

Examples:

- Order ID
- Order Status
- Quantity
- Order Creation Date
- Deal Price

### `Derived`

The field was created by the ETL from existing source information.

Examples:

- `product_key`
- `date_key`
- `shipping_key`
- `payment_key`
- `final_base_product_name`
- `final_category`
- `order_year`
- `is_cancelled`

This distinction documents where each field came from and supports traceability during validation and defense.

## ETL Process

### 1. Extract

All historical Shopee order files were read from the raw data folders using Python, Pandas, and OpenPyXL.

The raw exports were preserved and were not manually overwritten.

### 2. Consolidate

The historical files were combined into one raw transaction dataset.

Initial combined result:

- **226,205 transaction rows**
- **62 combined columns including ETL source-tracking fields**

### 3. Profile

The combined dataset was profiled before cleaning.

Checks included:

- missing values
- duplicate rows
- transaction-line duplicates
- dates
- quantities
- returned quantities
- prices and financial values
- Order Status
- cancellation information
- return/refund information
- SKU completeness
- schema differences across source exports

### 4. Clean

Cleaning was intentionally conservative.

Records were not deleted merely because optional fields were blank.

Examples:

- blank cancellation fields can be valid for non-cancelled orders
- blank return/refund fields can be valid
- missing SKU values were preserved
- original financial signs were preserved
- possible duplicates were not removed unless confirmed

Two confirmed redundant source-level duplicate copies were removed.

### 5. Transform

The ETL created fields needed for consistent analysis and database relationships.

Examples:

- stable product identifiers
- concise analytical product names
- final analytical categories
- calendar/date fields
- status flags

### 6. Validate

The final outputs were checked for:

- row-count reconciliation
- missing product identifiers
- missing final names
- missing categories
- duplicate dimension keys
- orphan foreign keys
- category reconciliation
- order-level conflicts
- retained transaction consistency

## Important Product Identifier Decision

The Shopee export contains Parent SKU and SKU fields, but historical completeness is extremely low:

- **Parent SKU missing:** 226,202 rows (99.9987%)
- **SKU missing:** 225,372 rows (99.6318%)

Because of this, SKU cannot safely serve as the sole historical product identifier.

The ETL therefore preserves Shopee SKU values when available but does **not fabricate missing SKU values**.

Instead, the ETL uses `product_key` as its governed product/variation identifier:

### `product_key`

A stable deterministic internal identifier for a product and variation.

Example:

`prd_674aed826cd81868e420426fa22edb62e1c40894eb25761174e21b67394eed19`

This key is used for internal joins and referential integrity.

`product_key` is intentionally technical and does not need to be displayed to
end users. Human-facing dashboards and reports should primarily display
`final_base_product_name` while retaining `product_key` behind the scenes for
stable joins.

---

## Product Names

The original Shopee `Product Name` is always preserved.

Shopee listing names often contain:

- SEO/search keywords
- repeated synonyms
- English/Filipino duplicates
- promotional phrases
- long lists of uses or target users

A separate field, `final_base_product_name`, was created for analysis and dashboard readability.

Example:

Original Shopee title:

`Reusable Poncho Breathable Lightweight Waterproof Hiking Kapote Makapal Unisex Men Women Hood`

Analytical name:

`Reusable Waterproof Poncho`

The original title is still retained for traceability.

`Variation Name` is also retained because it can distinguish seller-defined versions such as color, size, packaging, or model.

---

## Product Categories

Historical Shopee category information was incomplete/inconsistent, so a controlled analytical taxonomy was created for the capstone.

Final result:

- **713 analytical base products**
- **2,116 product/variation keys**
- **20 analytical categories**

The category field is intended for the capstone's analytical grouping and should not be interpreted as an exact copy of the seller's current Shopee storefront/display categories.

Promotional collections such as `On Sale` and `New Arrival` are not treated as analytical product categories.

# Final Data Architecture

The final database-ready outputs use a **star-schema structure**.

The central table is:

`fact_sales`

It contains one row per cleaned transaction line and links to the dimension tables.

```text
                         +------------------+
                         |   dim_product    |
                         |------------------|
                         | product_key      |
                         | product name     |
                         | variation        |
                         | category         |
                         +---------+--------+
                                   |
                                   |
+------------------+               |
|     dim_date     |               |
|------------------|               |
| date_key         |               |
| full_date        |               |
| year/month/etc.  |               |
+---------+--------+               |
          |                        |
          |                        |
          |          +-------------v-------------+
          +--------->|         fact_sales        |
                     |---------------------------|
                     | sales_line_key            |
                     | Order ID                  |
                     | product_key               |
                     | date_key                  |
                     | shipping_key              |
                     | payment_key               |
                     | Quantity                  |
                     | Returned Quantity         |
                     | prices / discounts / fees |
                     +------+----------+---------+
                            |          |
                   +--------+          +--------+
                   |                            |
          +--------v---------+        +---------v--------+
          |   dim_shipping   |        |   dim_payment    |
          |------------------|        |------------------|
          | shipping_key     |        | payment_key      |
          | tracking         |        | descriptors      |
          | shipping option  |        | invoice fields   |
          | shipment method  |        | bundle flags     |
          | destination      |        +------------------+
          +------------------+

                     +------------------+
                     |    dim_order     |
                     |------------------|
                     | Order ID         |
                     | Order Status     |
                     | Cancel reason    |
                     | Return/Refund    |
                     | order timestamps |
                     +------------------+
                              ^
                              |
                              +---- fact_sales.Order ID
```

---

## How the Tables Are Interconnected

### `fact_sales` → `dim_product`

Relationship:

`fact_sales.product_key = dim_product.product_key`

Purpose:

Connects every sales transaction line to the correct product/variation record.

`product_key` is the internal stable relationship key. Reports should display
`final_base_product_name` rather than exposing the technical key where possible.

---

### `fact_sales` → `dim_date`

Relationship:

`fact_sales.date_key = dim_date.date_key`

Purpose:

Connects transactions to the calendar dimension so later analysis can group data by:

- date
- month
- quarter
- year
- day of week

---

### `fact_sales` → `dim_order`

Relationship:

`fact_sales.Order ID = dim_order.Order ID`

Purpose:

Connects transaction lines to order-level information such as:

- Order Status
- cancellation reason
- return/refund status
- order timestamps

One Shopee Order ID may contain multiple product transaction lines, which is why Order ID alone was **not** treated as a duplicate-record key.

---

### `fact_sales` → `dim_shipping`

Relationship:

`fact_sales.shipping_key = dim_shipping.shipping_key`

Purpose:

Connects transaction lines to the available shipping and destination context, such as:

- tracking number
- shipping option
- shipment method
- available destination/location fields

---

### `fact_sales` → `dim_payment`

Relationship:

`fact_sales.payment_key = dim_payment.payment_key`

Purpose:

Connects transaction lines to the available payment/invoice descriptor context.

Transaction monetary measures remain in `fact_sales` where appropriate.

---

## Referential Integrity

The final validation confirmed that the star-schema relationships are connected correctly.

Validation includes:

- no duplicate dimension keys
- no orphan product keys
- no orphan date keys
- no orphan shipping keys
- no orphan payment keys
- no missing final analytical product names
- no missing final categories

This means a fact-table foreign key does not point to a missing dimension record.

---

## Duplicate Handling

Duplicate detection was performed before deletion.

The ETL did **not** simply use:

`df.drop_duplicates()`

and did not treat repeated Order IDs as automatic duplicates.

This is important because one Shopee order can legitimately contain multiple product lines.

The profiling process identified:

- 4 exact duplicate rows
- forming 2 confirmed duplicate groups

Fresh Shopee re-downloads confirmed that the same duplicate records existed in the original source exports.

Only the redundant copy from each confirmed duplicate pair was removed.

Result:

- Raw rows: **226,205**
- Redundant copies removed: **2**
- Final cleaned rows: **226,203**
- Exact duplicates remaining: **0**

Possible transaction-line duplicates that were not proven to be errors were preserved.

# Important Usage Rules

1. Use the files inside `final_outputs/` for the analytics stages.
2. Do not manually edit raw Shopee exports.
3. Do not replace the original Shopee Product Name with the analytical name.
4. Do not fabricate missing SKU values.
5. Do not delete repeated Order IDs simply because they repeat.
6. Keep `product_key` for internal joins.
7. Display `final_base_product_name` in human-facing dashboards and reports.
8. If a data issue is discovered later, report it to Member 1 so it can be corrected through the ETL process rather than manually modifying the final dataset.
